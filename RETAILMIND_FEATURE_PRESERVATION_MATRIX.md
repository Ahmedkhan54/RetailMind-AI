## Remaining database-dependent work

No database-backed feature was modified to simulate durable storage. The following requires a working, disposable MySQL environment and explicit verification before it can be claimed complete:

1. Resolve the existing MySQL 1045 credentials/grant issue, then apply the repository's existing auth, session, user-owned upload, report, and preference SQL migrations to a disposable schema. Do not apply them to production data as part of this continuation.
2. Exercise registration, sign-in/out, HttpOnly session validation/revocation, password changes, profiles, account roles, owner-only controls, audit privacy, and preference CRUD through the real database-backed auth service.
3. Verify upload metadata and private file storage create/list/read/delete, dataset reload after API restart, checksum/path validation, per-user isolation, and the configured durable `RETAIL_UPLOAD_STORAGE_DIR`.
4. Persist column-mapping edits (currently API-process memory only) and, if manual worksheet choice is added, persist the selected worksheet per uploaded workbook so reloads cannot silently switch sheets.
5. Verify account-scoped goal create/list/delete and dataset/date-range progress; saved-report metadata create/search/filter/delete and export reapplication; and account/session/audit views.
6. Design and verify user-scoped durable alert acknowledgment/dismissal state; keep these actions unavailable until an approved persistent schema/API exists.
7. Choose and verify durable per-user RAG document/index storage with a clear lifecycle and deletion model; current RAG state is process-memory only.
8. Decide whether to add user-scoped dashboard definitions/pages/themes/save history (including autosave and undo/redo). The full canvas editor is not implemented because process-local or mock persistence is not an acceptable substitute.
